# 안티그라비티 전달용 마스터 프롬프트

아래 작업은 신규 프로젝트를 처음부터 다시 만드는 일이 아니다. 현재 폴더에 존재하는 코드·에셋·설계 JSON·샘플 화면을 먼저 읽고, 망가졌거나 미완성인 부분을 안전하게 복구한 뒤 기능과 품질을 높이는 작업이다.

프로젝트명은 **「세계를 잇는 여행」**이다. 초등학교 고학년~중학생 대상의 세계지도·다문화 교육게임이며, 정보 암기형 퀴즈보다 관찰·근거 판단·관점 전환·경청·공감·선택 결과를 경험하게 하는 것이 핵심이다.

## 0. 절대 지침

1. 현재 프로젝트를 통째로 새로 만들거나 기존 구조를 전면 교체하지 마라.
2. 기존 파일, 라우트, 컴포넌트, 에셋, 저장키, 정상 동작 기능을 임의로 삭제하지 마라.
3. `rm -rf`, `git reset --hard`, `git clean`, 잠금파일 재생성, 의존성 전체 교체, 프레임워크 마이그레이션을 금지한다.
4. 기존 사용자 수정사항과 미커밋 파일을 절대 덮어쓰지 마라.
5. 먼저 읽기 전용 진단을 수행하고, 변경 전에 복구 기준점을 기록하라.
6. 대규모 코드 삭제는 금지한다. 명백한 버그를 고치기 위한 최소 줄 교체가 불가피하다면 기존 동작을 테스트로 고정하고 변경 이유를 최종 보고서에 기록하라.
7. 사용되지 않는 것으로 보이는 코드도 즉시 삭제하지 마라. 참조 관계를 확인하고 `삭제 후보`로만 보고하라.
8. 같은 기능의 새 컴포넌트·서비스·유틸리티를 중복 생성하지 마라. 먼저 기존 구현을 찾아 재사용·보강하라.
9. 임시 이름의 `NewButton`, `Button2`, `FinalModal`, `GameSceneCopy`, `utils-new` 같은 중복 코드를 만들지 마라.
10. 디자인을 맞춘다는 이유로 게임 로직·저장 데이터·접근성을 희생하지 마라.
11. 에셋이 존재하면 반드시 그것을 우선 활용하고, 비슷한 새 이미지를 임의 생성하지 마라.
12. 한글 본문, 버튼, 카드, 말풍선, 진행률, 점수는 이미지에 굽지 말고 HTML/CSS/SVG로 구현하라.
13. 한 이미지에 여러 에셋이 들어간 콜라주·시트·합본을 새로 만들지 마라. `1이미지=1에셋` 원칙을 유지하라.
14. 사실을 추측해서 채우지 마라. 파일이나 JSON에서 확인되지 않는 것은 `확인 필요`로 표시하라.
15. 핵심 게임은 외부 API가 끊겨도 실행되어야 한다. 외부 API를 필수 런타임 의존성으로 추가하지 마라.
16. 먼저 복구하고 그다음 개선하라. 한 번에 대규모 리팩터링하지 말고, 단계마다 빌드와 테스트를 통과시켜라.
17. 사용자가 별도로 요청하지 않은 배포, 저장소 초기화, 원격 푸시, 브랜치 삭제를 하지 마라.

## 1. 가장 먼저 확인할 자료와 우선순위

현재 프로젝트 루트를 기준으로 모든 파일을 조사하라. 아래 파일이 있으면 반드시 전체 내용을 읽는다.

### 최종 설계 기준

- `world-map-multicultural-page-prompts.json`

이 파일이 현재 확정된 제목, 1~10페이지 구성, 학습 흐름, 화면 프롬프트, 상호작용, 저장 계약, 에셋 계획, 검수 기준의 최우선 근거다.

### 보조 설계 자료

- `world_passport_game_design_v1.json`

이 파일은 이전 설계이므로 저장 안정성, 오류 복구, 교사 모드, 유지보수, 테스트 항목만 보조로 참고한다. 이 파일의 예전 제목이나 예전 페이지 구조가 최종 설계를 덮어쓰면 안 된다.

### 자료 충돌 시 우선순위

1. 이 프롬프트의 절대 지침
2. `world-map-multicultural-page-prompts.json`
3. 페이지별 샘플 화면 이미지의 시각적 구성
4. 현재 폴더의 실제 에셋
5. 현재 정상 작동하는 기존 기능과 저장 호환성
6. `world_passport_game_design_v1.json`의 비충돌 보조 항목

샘플 화면과 JSON이 충돌하면 화면의 시각적 위계·배치·분위기는 샘플을 참고하고, 학습 내용·진행 조건·저장·채점·접근성은 최종 JSON을 따른다.

### 절대 바꾸면 안 되는 최종 정보

- 최종 제목: `세계를 잇는 여행`
- 예전 제목 `월드 패스포트: 다름을 잇는 여행`로 되돌리지 않는다.
- 예전 페이지명 `WORLD LINK`, `GEO SCAN`, `FLAG LAB` 등을 최종 화면명으로 복원하지 않는다.
- 최종 10페이지:
  1. 세계를 잇는 여행
  2. 세계 항로 지도
  3. 나의 여행 여권
  4. 아시아: 하루를 읽는 탐험
  5. 유럽: 흔적과 오늘의 도시
  6. 아프리카: 소리의 대화
  7. 아메리카: 우리 반의 하루
  8. 오세아니아: 함께 지키는 섬과 바다
  9. 다름을 잇는 대화
  10. 세계 연결 인증

## 2. 1단계: 변경 전 읽기 전용 진단

코드를 수정하기 전에 다음을 수행하고 결과를 간단히 기록하라.

1. 프로젝트의 실제 기술 스택, 패키지 매니저, 빌드 도구, 라우팅 방식, Phaser/Three.js 사용 여부를 확인한다.
2. `package.json`, lockfile, 설정 파일, 환경 변수 예시, 기존 README, 모든 JSON 설계 파일을 읽는다.
3. `git status`, 현재 브랜치, 현재 HEAD를 확인한다. 미커밋 변경은 사용자 작업으로 간주하고 보존한다.
4. 기존 실행 명령을 찾아 현재 상태 그대로 install, typecheck, lint, test, build를 시도한다.
5. 실패 항목은 수정 전 오류 원문과 재현 명령을 기록한다.
6. 현재 라우트, Scene, 컴포넌트, 서비스, 저장키, EventBus 이벤트, 에셋 import 관계를 목록화한다.
7. 샘플 화면 파일을 `sample`, `mockup`, `reference`, `screen`, `page`, `design` 등의 이름으로 찾아 페이지 1~10과 연결한다.
8. 이미지, WebP, PNG, SVG, GLB, 오디오 파일을 전수 조사하되 파일을 이동하거나 이름을 바꾸지 않는다.
9. 에셋마다 경로, 크기, 확장자, 알파 유무, 파일 용량, 사용 페이지, 현재 import 위치를 기록한다.
10. 내용이 같은 파일은 해시로만 중복 여부를 판정하고, 발견 즉시 삭제하지 않는다.
11. 로컬 저장 데이터를 읽는 코드가 있다면 스키마와 파싱 실패 처리 여부를 확인한다.
12. 페이지 이동, 뒤로가기, 새로고침, 빠른 연타에서 중복 Scene 또는 중복 보상이 발생하는지 확인한다.

진단 결과는 `docs/recovery-baseline.md`에 기록한다. 이 파일이 이미 있으면 덮어쓰지 말고 날짜가 포함된 새 섹션을 추가한다.

## 3. 안전한 복구 기준점

1. Git 저장소라면 현재 변경을 손상시키지 않는 방식으로 작업하라.
2. 새 브랜치 생성이 허용되는 환경이면 `repair/world-connection-journey` 같은 별도 브랜치를 사용하되, 미커밋 파일을 임의 stash 또는 reset하지 마라.
3. 브랜치 생성이 불가능하면 수정 전 파일 목록과 해시를 `docs/recovery-baseline.md`에 남긴다.
4. 기존 파일을 교체해야 한다면 동일 경로의 기능 계약을 유지하고, 변경 전 동작을 테스트로 먼저 고정한다.
5. 삭제 대신 호환 래퍼, 어댑터, legacy route redirect, deprecated 표기를 우선한다.
6. 기존 저장키를 변경하지 말고, 새 스키마가 필요하면 마이그레이션을 추가한다.

## 4. 에셋 사용 원칙

현재 폴더의 모든 에셋을 먼저 활용한다. 새 에셋 생성은 하지 않는다.

### 3D 변환 참고 이미지

다음 파일이 있다면 Meshy용 원본 참고 이미지 또는 2D fallback으로 분류한다.

- `assets/meshy-references/character_explorer_base.png`
- `assets/meshy-references/aircraft_world_traveler.png`
- `assets/meshy-references/prop_globe_blank.png`
- `assets/meshy-references/prop_passport_open.png`
- `assets/meshy-references/portal_continent_gateway.png`
- `assets/meshy-references/prop_empathy_compass.png`
- `assets/meshy-references/prop_puzzle_globe.png`
- `assets/meshy-references/prop_world_map_table.png`
- `assets/meshy-references/prop_passport_stamp.png`
- `assets/meshy-references/reward_world_connector_badge.png`

PNG 참고 이미지를 GLB처럼 취급하지 마라. 실제 GLB가 없으면 PNG를 2.5D fallback으로 사용하고, 3D 로더 실패를 발생시키지 마라.

### 에셋 인벤토리

1. `src/assets/asset-manifest.ts` 또는 기존 manifest가 있으면 그 파일을 확장한다.
2. manifest를 새로 만들기 전에 기존 에셋 레지스트리와 로더를 찾는다.
3. 에셋은 파일 경로를 화면 코드에 반복 하드코딩하지 말고 semantic id로 참조한다.
4. 예: `hero.explorer`, `vehicle.airplane`, `prop.passport`, `portal.continent`, `reward.badge`.
5. 실제 파일명과 대소문자를 그대로 보존한다.
6. 경로를 바꿔야 한다면 모든 import를 한 번에 검증하고 기존 경로에는 호환 alias를 남긴다.
7. 원본 PNG를 덮어쓰지 말고, 배포 최적화본이 필요하면 별도의 WebP 파일을 만든다.
8. 투명 에셋은 알파를 보존한다.
9. 이미지 에셋은 페이지당 최대 10개를 넘지 않게 하고 공통 에셋은 캐시해 재사용한다.
10. 버튼, 카드, 탭, 체크박스, 게이지, 모달 프레임은 이미지로 만들지 않는다.
11. 지구본과 작전 테이블의 세계지도는 AI 이미지에 의존하지 말고 정확한 SVG 또는 검증된 지도 텍스처를 코드에서 적용한다.

### 9페이지 필수 독립 에셋

최종 JSON의 다음 semantic asset을 찾아 실제 파일과 연결하라. 없으면 빈 파일이나 깨진 URL을 만들지 말고 CSS fallback과 `missing asset report`를 제공한다.

- 모로코 인사 어린이
- 콜롬비아 인사 어린이
- 일본 목례 어린이
- 탄자니아 인사 어린이
- 호주 인사 어린이
- 네팔 두손인사 어린이
- 하트 말풍선 아이콘
- 경청 귀+하트 아이콘
- 공감 나침반
- 퍼즐 지구본

각 이미지는 독립 파일이어야 하며 콜라주·시트로 합치지 않는다.

## 5. 샘플 화면 일치 기준

샘플 화면은 최종 UI의 시각적 기준이다. 단순히 비슷한 색만 쓰지 말고 아래 항목을 분석해 구현한다.

1. 화면 전체 정보 위계
2. 제목·핵심 오브젝트·카드·버튼의 상대적 크기
3. 주요 오브젝트 위치와 여백
4. 배경의 깊이감과 전경·중경·후경 관계
5. 보라, 하늘색, 청록, 산호색, 금색의 사용 비율
6. 모서리 반경, 테두리, 그림자, 강조 상태
7. 페이지별 서로 다른 레이아웃과 상호작용 구조
8. 캐릭터와 오브젝트가 UI를 가리지 않는지 여부
9. 16:9 화면의 안전 영역
10. 초등 고학년에게 친근하지만 유치원용처럼 보이지 않는지 여부

샘플 화면에 한글이 이미지로 포함돼 있어도 실제 구현에서는 DOM 텍스트로 다시 만든다. 이미지 속 잘못된 글자를 그대로 사용하지 않는다.

1920×1080, 1366×768, 1024×576에서 페이지별 스크린샷을 만들고 다음을 비교한다.

- 주요 블록 배치
- 안전 여백
- 글자 잘림
- 카드 겹침
- 버튼 터치 영역
- 캐릭터·오브젝트 크기
- 모바일 브라우저 주소창 변화 시 레이아웃 안정성

시각적 유사성을 올리되 픽셀 고정 좌표를 남발하지 말고 CSS Grid, Flex, `clamp()`, `aspect-ratio`, container query 또는 기존 반응형 체계를 사용한다.

## 6. 구현 구조

기존 기술 스택을 유지한다. 새 프레임워크로 갈아엎지 않는다.

### 역할 분리

- Phaser: 드래그, 분류, 순서 배열, 지도 노드, 리듬, 퍼즐, 결과 연출
- DOM/CSS/SVG: 한글, 버튼, 카드, 퀘스트, 말풍선, 설정, 모달, 인증서, 접근성
- EventBus: Phaser와 DOM 사이의 상태 전달
- JSON: 페이지, 문항, 미션, 채점, 저장, 에셋 semantic id
- Three.js: 실제 공간 탐색이나 고정 3D 미리보기에 필요할 때만 사용

Three.js와 Phaser를 동시에 계속 렌더링하지 마라. Three.js Scene을 사용하는 화면에서 Phaser 미션으로 전환하면 Three 렌더 루프를 정지하고, 복귀할 때만 재개한다. 숨겨진 canvas에서 애니메이션을 계속 돌리지 않는다.

현재 게임은 안정적인 2D·2.5D 완성이 우선이다. GLB가 아직 없으면 3D 구현을 억지로 추가하지 말고 PNG fallback으로 완성한다. 향후 GLB를 연결할 수 있도록 AssetManager 인터페이스만 준비한다.

### 권장 DOM 레이어

```html
<div id="game-shell">
  <div id="three-root"></div>
  <div id="phaser-root"></div>
  <div id="ui-overlay"></div>
</div>
```

기존 구조가 이미 안정적으로 존재하면 위 구조로 전면 개편하지 말고 같은 역할 분리만 유지한다.

### 공통 컴포넌트

기존 구현을 우선 검색하고 다음 기능을 공통화한다.

- Progress
- Modal
- Reward
- Toast
- BottomBar
- Settings
- LoadingFallback
- ErrorBoundary
- ConfirmDialog

공통화를 이유로 페이지별 고유 레이아웃까지 하나의 거대한 컴포넌트로 합치지 마라. 공통 상태와 시각 토큰만 재사용하고 각 페이지의 상호작용은 독립 모듈로 유지한다.

## 7. 페이지별 구현 계약

각 페이지는 `world-map-multicultural-page-prompts.json`의 해당 객체를 전체 읽고 구현한다.

### 1페이지

- 제목 에셋 `세계를 잇는 여행`을 사용한다.

- 저장 데이터가 없을 때 이어하기를 활성화하지 않는다.
- 첫 사용자 제스처 이전에 음악을 자동 재생하지 않는다.

### 2페이지

- SVG 히트영역을 가진 세계 항로 지도다.

- 3페이지 프로필 완료 후 대륙 탐험 순서는 자유롭게 선택할 수 있다.
- 다섯 대륙 완료 후 9페이지를 해금한다.

### 3페이지

- 닉네임은 실명 입력을 강제하지 않는다.
- 아바타 외모는 점수나 능력치에 영향을 주지 않는다.
- 비행기 선택은 시각적 선택이며 성능 차이를 만들지 않는다.
- 프로필은 로컬 저장하고 외부로 전송하지 않는다.

### 4페이지

- 사실, 가능한 해석, 판단 불가를 분류한다.
- 국가 전체를 하나의 생활방식으로 일반화하지 않는다.

### 5페이지

- 유럽 도시의 문화유산과 현재 생활을 함께 다룬다.
- 정답 경로를 하나로 고정하지 않는다.
- 자료 근거, 이동 효율, 접근성, 지역 존중을 종합 평가한다.

### 6페이지

- 아프리카를 하나의 음악 문화로 묶지 않는다.
- 듣기, 패턴 분석, 호출-응답 협력 미션을 구현한다.
- 오디오는 OGG와 MP3 또는 M4A 대체 파일을 함께 제공한다.
- 음소거 상태에서도 파형과 시각 박자로 진행할 수 있어야 한다.

### 7페이지

- 북·중·남아메리카의 다양한 학교·가정 사례를 다룬다.
- 필수 필요와 선호를 구분한다.
- 다수결을 자동으로 공정한 정답으로 처리하지 않는다.

### 8페이지

- 오세아니아를 호주 하나로 축소하지 않는다.
- 환경, 생활, 경제, 문화의 여러 관점을 비교한다.
- 지역 공동체의 동의와 참여를 필수 조건으로 둔다.

### 9페이지

- 국적만 보고 인사법을 맞히는 문제를 만들지 않는다.
- 모로코·콜롬비아·일본·탄자니아·호주·네팔의 인사 사례는 가능한 사례로만 제시한다.

### 10페이지

- 다섯 대륙 스탬프와 9페이지 완료를 다시 검증한다.

- 보상은 새로고침과 연타에도 한 번만 지급한다.

- 반·번호·이름 칸은 비워 두어 인쇄 후 직접 작성할 수 있게 한다.

## 8. 저장·이어하기·복구

최종 저장키는 가능한 한 다음 값을 유지한다.

```text
world_connection_journey.save.v1
```

기존 코드에 다른 저장키가 이미 사용 중이면 즉시 삭제하거나 무시하지 말고 legacy key를 읽어 새 스키마로 마이그레이션한다.

필수 원칙:

1. 저장 데이터는 `try/catch`로 읽는다.
2. 파싱 실패 시 앱을 멈추지 않는다.
3. 손상 데이터는 가능한 경우 별도 키로 백업한 뒤 안전한 기본값으로 복구한다.
4. 진행도는 배열 순서가 아니라 고정 id로 저장한다.
5. 앱 버전과 콘텐츠 버전을 분리한다.
6. 스키마 변경 시 `migrateSaveV1ToV2`처럼 명시적 마이그레이션을 둔다.
7. 각 미션 체크포인트에서 자동 저장한다.
8. 보상은 `rewardClaimedById`로 중복 지급을 막는다.
9. 저장 실패는 Toast로 알리되 게임을 즉시 종료하지 않는다.
10. 교사 초기화는 2단계 확인과 백업 내보내기 이후 실행한다.

## 9. 중복 실행과 Scene 안정성

다음 가드를 기존 구조에 맞게 적용한다.

- `isTransitioning`
- `isStageEnded`
- `resultShown`
- `inputLocked`
- `sceneToken`

필수 처리:

1. 빠른 연타와 다중 터치로 Scene이 두 번 전환되지 않게 한다.
2. 보상 모달과 결과 모달이 중복 표시되지 않게 한다.
3. 모든 EventBus 리스너는 Scene shutdown에서 해제한다.
4. 모든 타이머, interval, delayedCall을 종료 시 제거한다.
5. 오디오를 정지하고 참조를 해제한다.
6. Three.js를 사용한다면 전용 geometry, material, texture, renderTarget을 dispose한다.
7. 화면 밖 캐릭터 AnimationMixer를 정지한다.
8. 비동기 콜백은 현재 `sceneToken`과 일치할 때만 상태를 변경한다.
9. 동일 완료 요청이 여러 번 들어와도 결과가 한 번만 반영되는 idempotent 로직으로 만든다.

## 10. 성능 기준

학교 태블릿의 정확한 모델이 확정되지 않았으므로 보수적으로 설계한다.

- 저사양 목표: 30fps
- 일반 기기 목표: 45~60fps
- pixel ratio: 기본 1.0~1.25, 최대 1.5
- 첫 화면 필수 다운로드: 5~8MB 이내 목표
- 일반 텍스처: 512 또는 1024 우선
- 핵심 캐릭터만 최대 2048 허용
- 활성 HDR: 1K 1개 이하
- 동적 그림자: 핵심 오브젝트 1개 정도
- 후처리: 기본 비활성화
- 반복 오브젝트: 가능한 경우 재사용 또는 instancing
- 페이지별 에셋: 해당 페이지 진입 시 lazy loading
- 페이지 종료: 전용 에셋과 오디오 해제

모든 GLB, 배경, 음악을 앱 시작 시 한꺼번에 preload하지 마라.

## 11. UI·접근성

1. 16:9 태블릿 가로형을 우선하되 전자칠판과 데스크톱에서도 깨지지 않게 한다.
2. 버튼 최소 터치 영역은 44×44px 이상으로 한다.
3. 본문은 기본 18px 이상, 핵심 제목은 32~40px 범위에서 `clamp()`한다.
4. hover만으로 작동하는 기능을 만들지 않는다.
5. 키보드와 터치 모두 지원한다.
6. 색상만으로 정답·오답·잠금 상태를 표시하지 않는다.
7. 포커스 링을 제거하지 않는다.
8. 대화창, 버튼, 입력창에 적절한 aria-label을 제공한다.
9. `prefers-reduced-motion`에서 과도한 이동과 파티클을 줄인다.
10. 리듬 페이지에는 자막, 파형, 박자 점멸 등 청각 대체 정보를 제공한다.
11. 200% 확대에서도 핵심 진행이 가능해야 한다.

## 12. 문화 콘텐츠 안전

1. `이 나라 사람은 모두`, `항상`, `원래` 같은 일반화를 금지한다.
2. 국가, 대륙, 언어, 종교, 인종을 같은 개념으로 처리하지 않는다.
3. 전통의상만으로 국가를 식별하게 하지 않는다.
4. 피부색, 머리 모양, 옷차림을 성격이나 능력과 연결하지 않는다.
5. 낯선 행동을 틀린 행동으로 판정하지 않는다.
6. 모르는 점은 당사자에게 존중하는 방식으로 질문하도록 유도한다.
7. 인권 침해를 문화 차이로 정당화하지 않는다.
8. 문화 사실 데이터에는 출처, 검수일, 검수자, 고정관념 위험 메모를 둔다.
9. 출처가 없거나 검증되지 않은 사실을 임의로 추가하지 않는다.

## 13. 코드 품질과 1년 유지 구조

1. 현재 언어가 JavaScript라면 프로젝트 전체를 갑자기 TypeScript로 바꾸지 마라.
2. 현재 TypeScript라면 strict 오류를 새로 늘리지 마라.
3. 기존 lint와 formatter를 유지한다.
4. 새 의존성은 기존 코드로 해결할 수 없을 때만 추가하고 이유를 기록한다.
5. package 버전을 무조건 최신 major로 올리지 않는다.
6. lockfile을 유지한다.
7. 환경 변수는 `.env.example`에 이름과 용도만 기록하고 비밀값을 넣지 않는다.
8. 핵심 콘텐츠는 버전이 있는 JSON으로 분리한다.
9. 콘텐츠 id를 화면 배열 index와 결합하지 않는다.
10. 에셋 로더, 저장 서비스, 오디오 서비스, Scene 전환은 단일 책임으로 유지한다.
11. 페이지별로 같은 검증·저장·모달 코드를 복사하지 않는다.
12. 공통화는 기존 코드 재사용을 우선하며, 새 추상화가 오히려 복잡해지면 만들지 않는다.
13. 개발용 로그는 production에서 제거되거나 비활성화되어야 한다.
14. 오류 메시지는 사용자용과 개발자용을 분리한다.
15. 향후 에셋 추가가 코드 수정 없이 manifest 업데이트로 가능하게 한다.
16. 12개월 뒤에도 복구할 수 있도록 실행·빌드·테스트·배포 명령을 README에 고정한다.

### 7. 변경 파일

- 파일별 변경 이유
- 신규 파일
- 삭제 파일: 원칙적으로 `없음`

### 8. 남은 항목

- 추가 확인이 필요한 사실
- 아직 없는 에셋
- 사용자 판단이 필요한 선택
- 삭제 후보는 실행하지 말고 목록만 제공

## 18. 바로 작업 시작

이제 질문만 반복하지 말고 다음을 수행하라.

1. 프로젝트 루트와 핵심 파일을 읽는다.
2. 두 JSON의 충돌을 위 우선순위로 정리한다.
3. 에셋과 샘플 화면을 페이지별로 매핑한다.
4. 현재 빌드와 실행 오류를 재현한다.
5. `docs/recovery-baseline.md`에 기준점을 기록한다.
6. 복구 계획을 10줄 이내로 먼저 보고한다.
7. 치명적·비가역적 선택이 없으면 즉시 Phase B부터 구현을 계속한다.
8. 각 단계에서 테스트하며 초안을 완성한다.
9. 마지막에 위 최종 보고 형식으로 결과를 제출한다.

가장 중요한 목표는 **기존 프로젝트를 보존하면서 정상 작동 상태로 복구하고, 준비된 에셋·최종 JSON·샘플 화면을 실제 구현에 연결해 시각적 완성도와 학습 상호작용을 높이며, 1년 동안 유지 가능한 구조로 만드는 것**이다.
